# Term Crunch (`@tt/term-crunch`)

A terminal-skills challenge game built **entirely on `@tt/core`** to prove the engine-reuse pattern. basePath `/termverse/term-crunch`. Run via `npm run dev:crunch` / `npm run build:crunch`.

> Monorepo-wide context (`@tt/core`, tech stack, deploy) lives in the repo-root `.claude/CLAUDE.md`. The shared engine skills `tmux` and `commands` are at root; this app's own skills are `apps/term-crunch:{challenges,play-testing}`.

**Challenge copy (brief/instruction/hint): no filler.** One clause of scenario at most, then the objective; instructions are single imperatives; hints teach syntax/gotchas without wordy framing.

**Play-testing:** `scripts/play.ts` is a headless harness (`CrunchRunner` + REPL, `npm -w @tt/term-crunch run play`) — a thin shim over the real `runLine` + store, so it drives genuine game code. `scripts/playtest_tracks.ts` (`run playtest`, part of the root `npm run check` gate) plays every registry challenge end to end; **a new challenge needs a `SOLUTIONS` entry there** or the playtest fails. Chords and editor sessions can't be driven headlessly — see the `apps/term-crunch:play-testing` skill.

**It does NOT import termoil's story code** — no `gameStore`/`COMPUTERS`, story flags, emails/piper/chip (term-crunch has its own lean `useGameStore`). Anything shared must come through `@tt/core`, and `@tt/core/terminal/paneTypes` helpers must stay pure and store-agnostic. The reverse also holds — core must not carry termoil's story, or it surfaces here as dead commands: `src/__tests__/coreSurface.test.ts` asserts the core registry has no story builtins **and** that core's `SUBCOMMAND_MAP` completion table names nothing core doesn't register. The player-editable `~/.zshrc` + `~/.tmux.conf` (Settings modal) are parsed only via the shared `@tt/core` parsers (`terminal/tmuxConfig`, `terminal/envParse`) — never termoil's dotfiles or env-seeding code.

## Structure (`apps/term-crunch/src/`)

- **`challenges/`** — declarative challenge framework: `types.ts` (`Challenge`/`Step`/`ChallengeSnapshot`), `registry.ts` (ordered `CHALLENGES[]` — the challenge list lives there, one file per challenge), `categories.ts` (selectable tracks derived from challenge `type`: `all/tmux/git/fs/vim`), `scheduler.ts` (pure SM-2-lite spaced-repetition scheduler behind the completion-gate self-grades and the `review` command), `mastery.ts` (pure mastery-point/level module; MP is awarded at completion, never by grades). See the `apps/term-crunch:challenges` skill.
- **`state/gameStore.ts`** — lean Zustand store: ports `@tt/core` window/pane actions, drives win-detection via `checkCompletion()`, tracks `bestTimes`/`reviewStats`/`mastery`/`lastAwards`, and holds the player's `zshrc`/`tmuxConf` (persisted, `name: "term-crunch-progress"`). Win-detection and review-gate mechanics live in the challenges skill.
- **`components/`** — `GameShell.tsx` (layout), `TabManager.tsx` (thin adapter over the shared `@tt/core/terminal/useTabManager` hook; the app supplies store actions via `TabManagerAdapter` and the challenge-continue gate, per-pane `LineEditor`s, and editor/pager sessions via `TabManagerExtensions` — see the root `tmux` skill), `TabBar.tsx` (wraps the shared `TmuxStatusBar`), `SettingsModal.tsx` (`~/.zshrc` + `~/.tmux.conf` editors), `ChallengePanel.tsx` (category/challenge dropdowns — frozen while `isGradeGateUp` — plus Restart, Settings, and the `DueNotice`/`MasteryBlock` readouts), `Toast.tsx` (transient notices; MP awards deliberately do **not** toast), the target readouts `SchematicView.tsx`/`WindowStripView.tsx`/`FsTreeView.tsx`, and cheat sheets `CheatSheet.tsx` wrapped by `VimCheatSheet.tsx` (keep in sync with core `HELP_TEXTS.vim`) and `TmuxCheatSheet.tsx` (renders the prefix + binds parsed live from `~/.tmux.conf`; keep in sync with core `HELP_TEXTS.tmux` and the `handleChord` table).
- **`engine/commands/navigation.ts`** — app-local challenge-navigation builtins (`challenges`/`goto`/`next`/`prev`/`track`/`review`), always available and listed by `help` as cyan meta commands. Handlers only queue a pending navigation; `runLine` applies it after committing shell state so `loadChallenge`'s fresh seed isn't clobbered.
- **`hooks/useTerminal.ts`** — wires xterm to the store; `runLine` delegates to the shared `@tt/core/commands/runPipeline` (no redirection or file-read events — termoil opt-ins); side-effect-imports `lib/availabilityPolicy` and feeds the allowlist to the shared suggestions engine. Incomplete input is held in a zsh-style secondary prompt by the shared `LineEditor` before reaching `runLine`.
- **`lib/`** — `machine.ts` (`CRUNCH_MACHINE`/`HOME_DIR`), `availabilityPolicy.ts` (registers the `AvailabilityPolicy` enforcing each challenge's `commands` allowlist), `seed.ts` (`buildBaseFs()` + `applyConfigs`), `defaultConfigs.ts`, `gitState.ts` (git-state reader for validators), `seedFs.ts` (shared seed writers/readers used by every challenge `setup`), `paneCompare.ts` (structural pane-tree compare, ignores ids), `windowLabel.ts` (bakes in the `crunch` host).

## Window/pane UX

Mirrors the live game's tmux model (see the root `tmux` skill for the shared model, bindings, and conf parsing) — crunch-specific facts:

- Every challenge starts attached to tmux session `"0"` (`loadChallenge` seeds the session fields; transient, never persisted). While detached, the status bar, dividers, chords, and copy mode are gone and `checkCompletion` is **skipped** — unless the challenge sets `checkWhileDetached` (session-lifecycle challenges whose predicates read `snapshot.tmux`).
- The prefix key, status-bar theme, and pane focus/resize binds come from the **player-editable `~/.tmux.conf`** (Settings modal, default `DEFAULT_TMUX_CONF`); built-in chords remain as fallbacks for unbound keys.
- The `~/.zshrc` (also Settings-editable, default `DEFAULT_ZSHRC`) is seeded into every challenge's fs and its aliases/exports activated for the session.
